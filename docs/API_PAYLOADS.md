# API_PAYLOADS.md

## Start auth request

Browser redirect from tool:

```http
GET https://access-layer.unguess-internal.net/v1/auth/start?tool_slug=crm&return_url=https%3A%2F%2Fcrm.draftapps.it%2Fauth%2Fcallback&state=tool-generated-random-state
```

Required query params:

| Param | Required | Notes |
|---|---:|---|
| `tool_slug` | yes | Must match active registered tool |
| `return_url` | yes | Must match tool allow-list exactly or allowed strict pattern |
| `state` | yes | Opaque value generated by the tool to protect its own callback |
| `login_hint` | no | Optional email hint for Google account chooser |

## Tool callback after success

```http
GET https://crm.draftapps.it/auth/callback?code=otc_abc123&state=tool-generated-random-state
```

The code must be exchanged server-side. Do not process it in frontend-only code.

## POST /v1/auth/refresh

The tool backend calls refresh only as part of authenticated user activity, when the current access token is expired or close to expiration. Do not run unconditional background refresh timers.

Request headers:

```http
Authorization: Basic base64(tool_client_id:tool_client_secret)
Content-Type: application/json
```

Request body:

```json
{
  "refresh_token": "rt_current-opaque-refresh-token"
}
```

The successful response has the same identity/session shape as `/v1/auth/exchange`, with a new `access_token`, a new `refresh_token` and the extended `session.expires_at`. The submitted refresh token is revoked atomically and must be discarded immediately.

An invalid, expired, already-used or no-longer-authorized refresh returns `401 AUTH_REFRESH_TOKEN_INVALID`. The tool must clear its local session and restart the login flow; it must not retry the same refresh token.

Request:

```json

  "slug": "crm",
  "display_name": "CRM interno",
  "description": "Tool CRM interno",
```

```json

  "tool": {
    "id": "tool-id",
    "slug": "crm",
    "display_name": "CRM interno",
    "description": "Tool CRM interno",
    "status": "active",
```

Non-empty grant permissions must exist in `permission_keys` / `tool_permissions` for the tool.

## Bulk grant import/export

### GET /v1/admin/grants/bulk/template

Returns a CSV template:

```csv
email,tool_slug,role,permissions,valid_until,action,note
mario.rossi@unguess.io,petyr,tool_user,petyr:read:all,,upsert,Accesso Petyr
luca.verdi@unguess.io,petyr,tool_user,,,revoke,Revoca accesso
```

### GET /v1/admin/grants/export

Returns current grant rows as CSV with at least:

```csv
email,tool_slug,role,permissions,status,valid_from,valid_until,grant_id,user_id
```

### GET /v1/admin/tools/permissions/export

Returns the available tool/permission catalog as CSV:

```csv
tool_slug,tool_name,tool_status,permission_key,permission_description
petyr,Petyr,active,petyr:read:all,
```

### POST /v1/admin/grants/bulk/preview

Il separatore viene rilevato automaticamente dalla riga di intestazione: sono supportati sia `,` sia `;`. Le API client possono anche inviare esplicitamente `delimiter` con uno dei due valori.

Request:

```json
{
  "content": "email,tool_slug,role,permissions,valid_until,action,note
mario.rossi@unguess.io,petyr,tool_user,petyr:read:all,,upsert,Accesso Petyr
"
}
```

Response:

```json
{
  "rows": [
    {
      "row": 2,
      "email": "mario.rossi@unguess.io",
      "tool_slug": "petyr",
      "role": "tool_user",
      "permissions": ["petyr:read:all"],
      "valid_until": null,
      "action": "upsert",
      "result": "ok",
      "reason": null,
      "resolved_user": "pending_user_link",
      "status_after": "pending_user_link",
      "operation": "create"
    }
  ],
  "summary": { "total_rows": 1, "ok": 1, "warning": 0, "error": 0 }
}
```

### POST /v1/admin/grants/bulk/commit

Uses the same request body as preview. If preview contains validation errors, the endpoint returns `committed=false` and does not write grants. If there are no errors, it creates, updates or revokes matching grants and writes per-row audit events plus `admin.grant.bulk_import_committed`.

Supported CSV actions:

- `upsert`: create a new grant, or update an existing active/pending grant for the same email/tool/role;
- `revoke`: revoke non-revoked grants matching email/tool and optional role, and revoke their active sessions.

Known users become `active` grants; unknown but allowed company emails become `pending_user_link` grants and are linked automatically at first verified Google login.

## DELETE /v1/admin/tools/{tool_id}

Deletes a non-reserved tool registration. Cascading database relations remove linked client credentials, permission keys, grants, sessions and pending auth/access requests. Audit log rows are preserved; `audit_logs.tool_id` is set to null while `tool_slug` remains searchable/readable.

The reserved `access-admin` tool cannot be deleted.

Response:

```json
{
  "tool": {
    "id": "tool-id",
    "slug": "crm",
    "display_name": "CRM operativo",
    "status": "active",
    "allowed_return_urls": ["https://crm.draftapps.it/auth/callback"],
    "permission_keys": ["crm:read", "crm:write", "petyr:read:all"]
  }
}
```

## POST /v1/admin/tools/{tool_id}/rotate-secret

Request:

```json
{
  "revoke_existing": false
}
```

When `revoke_existing=true`, existing active tool clients are disabled before the new client credential is created. The new `tool_client_secret` is still shown once only.

## Access request reopen delay

`ACCESS_REQUEST_REOPEN_AFTER_DAYS` controls when a rejected or closed request can create a new pending request for the same `tool_id + email_normalized`.

Default v1 behavior:

- pending duplicate attempts increment `attempts_count`;
- attempts after a recent rejection/closure write audit `access_request.reopen_suppressed`;
- a new pending request can be created after the configured delay.

Response:

```json
{
  "grant_id": "grt_01HY...",
  "status": "active",
  "link_status": "pending_user_link",
  "tool_slug": "crm",
  "email": "mario.rossi@unguess.io",
  "role": "tool_user",
  "permissions": ["crm:read", "crm:write"]
}
```
