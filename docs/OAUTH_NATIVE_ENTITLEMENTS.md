# OAuth native entitlements after Phase 9A.2

Status: **native protocol runtime implemented; native Admin writer/UI deferred**. Phase 9A.1 supplied migration 006. Phase 9A.2 uses it without a new migration. The frozen OAuth P0 contract in `OAUTH_P0_CONTRACT.md` and `specs/oauth-p0.v1.yml` remains the supported `legacy_bridge` compatibility profile. Native resources are available to controlled SQL fixtures; `/admin/oauth` still creates legacy-bridge resources only.

## Phase 9A.2 runtime decision

The current resource `entitlement_mode` selects exactly one evaluator. `legacy_bridge` retains the P0 binding, explicit legacy permission mapping and legacy grant logic. `native` requires an active internal `users.id`, active resource/client, active canonical scope registration and exact client/resource/scope allowance for **every** requested scope. Each scope must have one linked, active, unrevoked `oauth_native_human_grants` row within `[valid_from, valid_until)`. Pending-email rows do not authorize and are never linked by the OAuth native callback. Unknown source/mode state fails closed; no branch falls back to the other.

The native callback rechecks registration and linked grants in the code issuance transaction. It writes `entitlement_source='native'`, a null legacy grant ID, one exact historical grant link per granted scope, the code row and transaction completion atomically. The writer independently repeats the current grant check and rejects duplicate/missing/mismatched provenance. P0 writes remain `legacy_bridge` with no native links.

Code exchange and refresh compare the authorization source with the current resource mode and re-evaluate current entitlement for the resulting scopes. A revoked, expired, pending, wrong-user or disabled grant yields `invalid_grant`; malformed/disallowed refresh narrowing retains `invalid_scope`. Online introspection also re-evaluates current entitlement and reports only `{"active":false}` on failure. Historical native provenance is audit evidence, never ongoing authorization truth. The local JWT still follows the frozen Google `sub` contract and may remain cryptographically valid until expiry; online introspection is the current-entitlement check.

Native evaluation takes PostgreSQL `FOR SHARE` locks on active client/resource/user, registration/allowance/scope and linked grant rows in canonical scope order. Code exchange and refresh retain their existing `FOR UPDATE` locks only on code or refresh family/session rows. Grant mutation waits for a transaction that has selected an effective grant; a mutation committed first is observed by the evaluator. Time is sampled after the grant locks using the later of the request clock and PostgreSQL clock. This defines the entitlement decision instant without broad table locks. Refresh replay retains the Step 4B atomic family/session revocation path.

Resource credentials authenticate only for introspection. Active resources in either mode are accepted. A disabled native resource may authenticate only to obtain `{"active":false}`; a disabled legacy-bridge resource is rejected. Draft resources in either mode are rejected. Native resource creation, grant mutation, explicit pending-email linking and controlled in-place resource transition remain deferred. Google is the only OAuth vNext upstream provider; the legacy Microsoft bridge is unchanged.

## Model

An OAuth resource has `entitlement_mode`: `legacy_bridge` or `native`. Migration 006 defaults every existing resource to `legacy_bridge` and blocks arbitrary direct mode UPDATE in this phase. P0 Admin creation omits the column and therefore continues to create legacy-bridge resources. For `legacy_bridge`, the existing active legacy-tool binding and exact registered legacy permission mapping remain mandatory at runtime. For `native`, there is no legacy binding or permission mapping. Both modes register exact canonical scopes through `oauth_resource_scopes`; no second resource/scope catalogue exists.

`oauth_native_human_grants` records one resource/scope pair and either a linked `users.id` or a normalized pending email. Linked `active` grants require `users.id`; pending grants require an email and no user link. Email is a pending address and optional audit snapshot, never a substitute for linked identity or proof that identities from two providers are the same. There is no account linking in 9A.1. Google remains the sole OAuth upstream provider. The temporary Microsoft bridge is legacy-only.

Only an exact registered scope is representable. No wildcard, prefix, segment, or legacy-permission conversion grants exist. A future evaluator must require `status='active'`, linked `user_id`, active user/resource/scope state, `valid_from <= now`, `valid_until IS NULL OR now < valid_until`, and no revocation. `expired` and `revoked` are terminal and ineligible. A grant cannot change its resource/scope or change an already linked user. A partial unique index permits at most one `active` row for a user/resource/scope; a separate index permits at most one pending row for an email/resource/scope. A validity deadline does not automatically update status, so a replacement row requires explicit expiry/revocation of the old active row. No timer or lifecycle writer exists yet.

The composite resource/scope FK and all user FKs use `ON DELETE RESTRICT`; audit history cannot disappear through parent deletion. `oauth_authorizations.entitlement_source` defaults to `legacy_bridge`; that source requires a legacy grant ID. A future `native` authorization requires the legacy grant ID to be null. At INSERT, a database trigger requires source to match the resource's current mode. The source, resource, user and granted scopes are then immutable historical facts; a later controlled resource-mode transition does not recheck old authorizations. P0 inserts continue using the default and their current legacy grant ID.

`oauth_authorization_native_grants` is a many-to-many historical link from native authorizations to the exact native human grant rows that justified their canonical scopes. The pair is unique, both FKs restrict deletion, and insertion requires a native authorization, the same linked user/resource, and a grant scope present in `granted_scopes`. One authorization may link multiple grants and a grant may justify multiple authorizations. The future writer must atomically verify active, in-window entitlement before recording links; the database checks stable identity/scope only so historical links remain restorable after later revocation. These links are audit provenance only: future refresh/introspection must re-evaluate current native entitlement, including expiry and revocation. There is no link writer in 9A.1.

The target migration for an existing resource is a privileged, audited **in-place** `legacy_bridge -> native` transition preserving `resource_id` and OAuth audience. A later operation must prevent unsafe mixed serving, terminate or safely revoke active legacy-derived OAuth sessions/authorizations, validate native scopes and provisioned grants, retire legacy bindings/mappings, and retain historical provenance. The exact API and transaction design remain deferred. Migration 006 blocks arbitrary UPDATE until that operation exists.

## Compatibility and restore

Migration 006 only adds columns, checks, triggers, indexes and two tables. It does not rewrite migrations 001–005 or existing rows. An older binary inserts legacy resources/authorizations using defaults. Its legacy entitlement joins fail closed if a future native resource or authorization is encountered. Until 9A.2, no native resource/grant writer is exposed by supported runtime or Admin behavior. A rollback must retain migration 006 and its rows; dropping the new columns/tables would lose native provenance and grants. Run the old-binary and N→N+1 smoke matrix on disposable PostgreSQL before deployment.

Encrypted full backup exports and imports the new columns, native grants and authorization-grant provenance in FK order. A complete pre-9A.1 17-section OAuth backup is accepted as having two empty native sections; a partial 18-section snapshot is rejected. Legacy-only backup remains accepted. Restore of an old snapshot cannot recover rows created after that snapshot, including future native grants. Before enabling a native writer, the compatibility window and restore procedure must be requalified after runtime changes.

An older binary can continue legacy issuance against the expanded schema and fails closed on native resources, as the disposable previous-binary smoke proves. Its old backup exporter cannot represent native grants or provenance; do not use an old-binary full backup as the recovery source after native rows exist. Full N→N+1 session/refresh survival still requires the separately documented immutable-version exercise and is not inferred from this schema smoke.

The 9A.2 work starts with a mode-aware, fail-closed entitlement evaluator and authorization/refresh/introspection provenance handling. Native grant Admin API and UI remain 9A.3.
