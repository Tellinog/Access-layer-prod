# DEPLOYMENT.md

## Step 1.5 continuity gate

Deployment remains prohibited while `operations/production-continuity.evidence.yml` is `NOT_READY`. Follow `operations/PRODUCTION_CONTINUITY_COLLECTION.md` to obtain live Coolify topology, exact PostgreSQL storage mapping, backup/restore, ownership and registry evidence. The validator is read-only and must not be used to populate deployment manifests automatically.

Do not rename `access_layer_postgres_data_v2` or `access_layer_postgres_data`, create a replacement production volume, alter Coolify configuration, or deploy as part of evidence collection.

## Infrastructure

- HTTPS termination with modern TLS.
- PostgreSQL with backups and point-in-time recovery.
- Secret manager.
- Centralized application logs.
- Monitoring for auth error rate, Google callback errors, DB write errors and audit log failures.
- Coolify/reverse-proxy deployments should set `TRUST_PROXY_HOPS=1`; direct local development should use `TRUST_PROXY_HOPS=0`.

## Local Docker Compose

The repository provides `docker-compose.yml` for local development:

- `postgres` uses PostgreSQL 16 and stores data in the `access_layer_postgres_data` volume.
- `app` builds the Node.js 22 service image, waits for PostgreSQL to become healthy, runs migrations, runs the local seed when `RUN_SEED_ON_START=true`, serves on port `8080`, and exposes a Docker healthcheck against the configured health path every 10 seconds.
- a Docker volume stores the local JWT private key generated by the app entrypoint when `JWT_PRIVATE_KEY_PEM_PATH` is configured and no key exists yet.

Setup:

```bash
cp .env.docker.example .env.docker
npm run docker:up
```

Use the npm scripts rather than plain `docker compose up`; they pass `.env.docker` as the compose environment file while keeping the PostgreSQL container limited to `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB`.

Required local edits before a real Google OAuth test:

When `RUN_SEED_ON_START=true`, the seed reconciles the reserved `access-admin` return URLs with the configured public base path. This helps existing local volumes move from older `/admin/auth/callback` data to `/access-control/auth/callback` without manually clearing PostgreSQL.

- set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`;
- set `ADMIN_BOOTSTRAP_EMAILS` to the initial admin email;
- replace local placeholder values for `POSTGRES_PASSWORD`, `SESSION_SECRET`, `TOOL_CLIENT_SECRET_PEPPER` and `LOG_IP_SALT`;
- replace `BACKUP_ENCRYPTION_KEY` before using backup export/import;
- keep `GOOGLE_REDIRECT_URI=http://localhost:8080/access-control/v1/auth/google/callback`;
- keep `GOOGLE_ALLOWED_HD=unguess.io,nuotounostiledivita.it`.

## Deploy sequence

1. Provision DB.
2. Apply schema migrations with `DATABASE_URL` configured; the migration runner does not require JWT or Google runtime secrets.
3. Create Google OAuth client and configure env for the confirmed local and production redirect URIs.
4. Generate JWT signing key and configure `kid`.
5. Deploy application.
6. Run health check.
7. Login as bootstrap admin.
8. Create admin grant and remove bootstrap env after verification.
9. Register pilot tool.
10. Run end-to-end tests.

## Rollback

Rollback must preserve audit logs and grants.

- Do not roll back DB migrations destructively without backup.
- If new JWT key is faulty, re-enable previous key and redeploy.
- If Google client config is faulty, restore previous redirect URI/client secret.


### Healthcheck log behavior

The repeated local Docker requests to `/access-control/health` are expected. They come from the `app.healthcheck` definition in `docker-compose.yml`, not from the browser UI.

The service keeps these checks enabled so Docker/Coolify can identify unhealthy containers, but the health routes use silent request logging to avoid normal log noise.
# Step 1 deployment block

Do not deploy the Step 1 compatibility-freeze commit. `docker-compose.yaml` mounts `access_layer_postgres_data_v2`, but the top-level volume declaration is `access_layer_postgres_data`. Neither side may be renamed until the live Coolify mapping is identified and a verified backup/restore point exists. The intended topology remains one Coolify Compose service, public app container port 8080 through HTTPS routing, private PostgreSQL and no public host-port mapping.
